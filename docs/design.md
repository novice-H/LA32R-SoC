## 1. 概述

### 1.1 两个目标与实施顺序

| 顺序             | 目标                             | 完成定义（DoD）                                                                                      |
| ---------------- | -------------------------------- | ---------------------------------------------------------------------------------------------------- |
| **目标一** | 在 LA32R SoC 上实现可游玩的 2048 | 上电后用板载按键在 DVI 显示器上完整游玩一局；数码管/LED 正确显示步数与状态；**全程零外部设备** |

### 1.5 地址映射

CPU 只识别三个从设备：

| 地址区间                           | 大小      | 设备                            | 用途                                                |
| ---------------------------------- | --------- | ------------------------------- | --------------------------------------------------- |
| `0x8000_0000` – `0x803F_FFFF` | 4 MB      | **BaseRAM**               | `.text` / `.rodata` / `.data` / `.bss` / 栈 |
| `0xA000_0000` – `0xA007_52FF` | 480 000 B | **ExtRAM**（FB0）         | 帧缓冲 0，120 000 字                                |
| `0xA008_0000` – `0xA00F_52FF` | 480 000 B | **ExtRAM**（FB1）         | 帧缓冲 1，120 000 字                                |
| `0xA010_0000` – `0xA015_FFFF` | 384 KB    | **ExtRAM**（AI 行移动表） | `next_row` 128 KB + `row_score` 256 KB          |
| `0xA018_0000` – `0xA01F_FFFF` | 512 KB    | **ExtRAM**（AI 转置表）   | `2^16 × 8 B`                                     |
| `0xBFD0_0000` – `0xBFD0_00FF` | 256 B     | **confreg**               | LED / 数码管 / 按键 / 拨码 / 计时 / FB_CTRL         |

> **AI 数据表放 ExtRAM 而不是 BaseRAM**：BaseRAM 要同时承受取指与访存，是最紧张的资源（见 2.2.5）；ExtRAM 除 DVI 扫描外几乎空闲，把大表搬过去是"把负载从瓶颈搬到空闲通道"。
> ExtRAM 总占用 = 960 000 B（双帧缓冲）+ 384 KB（AI 行表）+ 512 KB（转置表）≈ **1.79 MB / 4 MB = 45%**；BaseRAM 占用 ≈ 0.25 MB / 4 MB = **6%**。

### 1.6 五条设计原则

1. **单一时间域**：`clk_pix = clk_sys = 50 MHz`，视频与 CPU 同域，**没有一处 CDC**。
2. **显示与运算分片**：帧缓冲独占 ExtRAM，代码与栈独占 BaseRAM，两片 SRAM 物理隔离。
3. **DVI 极简**：DVI 只做"从固定地址扫描像素"一件事，不含任何 CPU 可编程逻辑；唯一控制是 1 根翻页请求线。
4. **确定性算法**：AI 全整数、全 `int32_t`/`uint32_t`，**同一份 C 源码在 PC 与板上结果必然相同**——这是无串口条件下验证 AI 的唯一可靠依据（见 3.6）。
5. **界面极简**：DVI 只画 4×4 棋盘，不画分数、标题、状态条。所有附加信息走数码管与 LED。

## 2. 目标一：2048 游戏

### 2.1 目标定义与验收标准

| 项             | 内容                                                                                                                                                                                                            |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **输入** | `touch_btn[3:0]` 四方向键；`key[0]` 游戏开关；`key[1]` 手动/AI 选择                                                                                                                                       |
| **输出** | DVI 800×600 显示 4×4 棋盘；数码管显示步数低 2 位；LED 显示步数高位与状态                                                                                                                                      |
| **验收** | ① 上电后拨上 `key[0]` 出现新局（两个随机块）② 四方向键可操作，非法方向无反应 ③ 步数随每次有效移动 +1 ④ 失败/胜利后画面冻结、对应 LED 亮、CPU 死循环等待 `key[0]` 重启 ⑤ **全程不接任何外部设备** |

### 2.2 硬件实现

#### 2.2.1 时钟与复位

```
clk_50M ──► PLL(pll_example, clk_out1 = 50 MHz) ──► clk_sys ──┬─► CPU / 总线 / SRAM
                                                               └─► clk_pix（同域）
```

**为什么仍过 PLL**：获得 BUFG 全局时钟网络、降低偏斜，并统一提供 `locked` 作为复位依据。

**复位策略：异步置位、同步释放**（全项目统一范式）：

```verilog
reg rst_sys;
always @(posedge clk_sys or negedge locked) begin
    if (!locked) rst_sys <= 1'b1;   // 异步置位：PLL 未锁定强制复位，避免 X 传播
    else         rst_sys <= 1'b0;   // 同步释放：所有触发器同一沿退出复位
end
```

`reset_btn` 接 PLL 的 `reset` 端口（照抄官方演示）。按下时 PLL 复位 → `locked` 拉低 → 经上述逻辑复位全片，因此 **`reset_btn` 是硬件级复位**，不参与游戏逻辑。

#### 2.2.2 LA32R CPU 集成

`la32r_wrap.v` 只做三件事，**不修改 IP 内部语义**：

1. **时钟复位接入**：`clk_sys` / `rst_sys`；
2. **接口归一化**：把 IP 的取指与访存端口转成内部统一主机接口；
3. **协议适配**：若 IP 提供 ready 握手，则在本层换成固定 2 拍应答（见 2.2.3）。

```verilog
// 内部统一主机接口契约
// 主机发出：m_addr[31:0] m_wdata[31:0] m_wstrb[3:0] m_req m_we
// 从机应答：m_rdata[31:0] m_ack（发起后第 2 拍拉高一拍）
```

> ⚠️ **待确认（Q3）**：赛方 IP 的访存时序是固定延迟还是握手、取指与访存是否共用端口。总线侧已按"固定 2 拍应答"设计，若 IP 不同，改动集中在本封装一处。

**LA32R 对软件有实质影响的特性**：

| 特性                                               | 依据        | 软件对策                                                                             |
| -------------------------------------------------- | ----------- | ------------------------------------------------------------------------------------ |
| GRLEN = 32，`r0` 恒 0，`r1` 为 `bl` 返回地址 | A03 §2     | 无 64 位寄存器                                                                       |
| 只有 `.w` 系列整数指令                           | A03 §2.2   | `long long` 由 libgcc 软实现（慢 10~30×）→ **AI 位板拆成 4×`uint32_t`** |
| 有 `mul.w/mulh.w/div.w/div.wu/mod.w`             | A03 §2.2.2 | 但 IP 是否实现需实测（T1.4）；未实现则靠 `-lgcc` 软乘除                            |
| 浮点指令在 ISA 中定义                              | A03 §3     | 精简 IP 通常不实现 → **AI 全程定点**                                          |
| **访存地址必须对齐**                         | A03 §2.1.4 | **所有绘制横坐标必须 4 的倍数**，否则触发地址错异常                            |

#### 2.2.3 总线译码与固定 2 拍应答

```verilog
wire sel_base = (addr[31:30] == 2'b10);   // 0x8000_0000 段
wire sel_ext  = (addr[31:28] == 4'hA);    // 0xA000_0000 段
wire sel_conf = (addr[31:8]  == 24'hBFD0); // 0xBFD0_0000 段
```

**统一应答原则：所有从设备固定 2 拍延迟应答。**

- 好处：CPU 侧只需一种等待状态，译码器与 CPU 解耦；
- SRAM 建立/保持时间（10 ns 器件）远小于 2 拍（40 ns），裕量充足；
- 外设也拉到同节拍，避免"某地址快、某地址慢"导致 CPU 微架构异常。

**为什么不做更快的单拍应答**：单拍要在一个周期内完成地址译码 + SRAM 读 + 数据回送，组合路径过长会压低 `clk_sys` 上限。2 拍是"时序松弛度"与"性能"的平衡点。若后期需要提速，第一优先级是提高 `clk_sys` 而非削拍数。

#### 2.2.4 BaseRAM 控制器

**芯片**：两颗 16 位 `IS61WV102416-10`（10 ns ≈ 100 MHz）拼成 32 位 × 4 MB。地址与 `CE/WE/OE` 共用，数据与字节使能分开。

**关键：`inout` 三态纪律。** `base_ram_data` 是双向总线，且顶层注释明确其**低 8 位与板上 CPLD 串口控制器共享**——总线可能存在第二个驱动源，三态控制错误会导致冲突。

```verilog
assign base_ram_data = (base_ram_we_n == 1'b0) ? base_wdata : 32'bz;
wire [31:0] base_rdata = base_ram_data;
```

**四条铁律**：

1. 只在 `we_n = 0` 时驱动写数据，其余时刻一律 `32'bz`；
2. `ce_n = 1` 时立即释放总线；
3. 读周期靠 `oe_n = 0` 让 SRAM 驱动，**FPGA 侧必须高阻**；
4. 上电/复位后默认 `ce_n = oe_n = we_n = 1`（顶层演示即如此，**必须保留**）。

**读时序（固定 2 拍）**：

```
clk        __/‾‾\__/‾‾\__/‾‾\__
req        ____/‾‾‾‾‾‾‾‾\______
addr       ====X< ADDR >X=======
ce_n/oe_n  ‾‾‾‾\_______________/‾
rdata      ============X<DATA>X_
ack        _______________/‾‾\___
```

第 0 拍锁存地址并拉低 `ce_n/oe_n`；第 1 拍 SRAM 数据稳定、采样并拉高 `ack`。

**写时序**：第 0 拍给出地址 + 数据 + `we_n=0`（`be_n` 按 `wstrb` 映射），第 1 拍撤销并拉高 `ack`。

`be_n[3:0]` 低有效，直接接 SRAM 的 `LB/UB`；**不使用字节使能时置 0（全字节使能）**，不可置 1。

#### 2.2.5 ExtRAM 控制器与双主机仲裁

ExtRAM 有**两个主机**：

| 主机          | 访问模式                 |
| ------------- | ------------------------ |
| **CPU** | 读/写，突发绘制矩形      |
| **DVI** | 纯读，每 4 像素读 1 个字 |

**仲裁策略：DVI 优先 + 水位保护。**

```
DVI 需要读 → 若 FIFO 水位低于高水位线，立即授予
CPU 请求   → DVI 无请求时授予；若 DVI 已在等，CPU 最多等待 1 拍
```

**为什么 DVI 优先是安全的**：DVI 只在有效视频区发请求，每 4 个像素时钟才需要 1 个字；一帧内共 120 000 次读，占 50 MHz 总带宽的 **17.3%**。CPU 拿到其余 82.7%，且最长阻塞仅 1 拍。

**带宽账**：

| 项目                             | 数值                                             |
| -------------------------------- | ------------------------------------------------ |
| ExtRAM 字速率（32 bit @ 50 MHz） | 50 M 字/s                                        |
| DVI 每行读次数                   | 800 px ÷ 4 = **200 字**                   |
| DVI 每帧读次数                   | 200 × 600 = **120 000 字**                |
| 刷新率                           | 50e6 ÷ (1040 × 666) = **72.19 Hz**       |
| **DVI 占用**               | 120 000 × 72.19 = **8.66 M 字/s = 17.3%** |
| AI 查表 + 转置表                 | ≈ 1.6 M 字/s = 3.2%                             |
| CPU 绘制 + 数据                  | ≈ 2 M 字/s = 4%                                 |
| **合计**                   | **≈ 25% ✅**                              |

**BaseRAM 才是真正的瓶颈**：若 CPU 为单发射流水且取指/访存共用一路 SRAM，理论需求 65 M 次/s > 50 M 次/s，**实际 IPC 约 0.6~0.8**。这取决于赛方 IP 微架构（Q3）。若需提速，按性价比依次：

1. 提高 `clk_sys` 至 66 / 80 MHz（SRAM 支持 100 MHz，瓶颈在 IP 与译码组合逻辑的时序收敛）；
2. 哈佛分离：代码留 BaseRAM，栈与数据挪到 ExtRAM 空闲区；
3. （若 IP 允许）加小容量指令缓存。

> 对 2048 这种回合制应用，IPC 0.7 完全够用；影响的是目标二 AI 的搜索吞吐（见 3.5）。

#### 2.2.6 confreg 外设

confreg 是 CPU 唯一的外设，承担全部板载输入输出与时间/随机服务。

**寄存器表**（基址 `0xBFD0_0000`）：

| 偏移      | 名称        | 方向 | 位域说明                                                                                                                                                               |
| --------- | ----------- | ---- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `+0x00` | `STEP`    | W    | `[11:0]` 步数 0~3199。硬件解码 → 数码管低 2 位 + `LED[4:0]` 高位                                                                                                  |
| `+0x04` | `STATUS`  | W    | `[15]`=AI 模式　`[14]`=游戏失败　`[13]`=游戏胜利　`[12:5]`=调试自由位                                                                                          |
| `+0x08` | `BTN`     | R    | `[3:0]` 按键单拍事件（`[0]`=上 `[1]`=下 `[2]`=左 `[3]`=右），**读后自动清除**                                                                          |
| `+0x0C` | `KEY`     | R    | `[1:0]` 拨码开关电平：`key[0]`=游戏开关，`key[1]`=AI 模式                                                                                                        |
| `+0x10` | `TIME`    | R    | `[31:0]` 毫秒计时（1 kHz 自由运行，约 49.7 天回绕）                                                                                                                  |
| `+0x14` | `RAND`    | R    | `[31:0]` 50 MHz 自由计数（随机种子；85.9 s 回绕，取差值即可）                                                                                                        |
| `+0x18` | `FB_CTRL` | W/R  | `[0]` 写 1 请求翻页（**VSYNC 翻转后由硬件清 0**，可轮询确认）；`[16]` **硬件独占**的当前显示缓冲号，CPU 只读（**整字写不会覆盖它**，见 2.2.7.3） |

**输出映射**（硬件直连）：

```verilog
assign leds[15]   = status[15];          // AI 模式
assign leds[14]   = status[14];          // 游戏失败
assign leds[13]   = status[13];          // 游戏胜利
assign leds[12:5] = status[12:5];        // 调试
assign leds[4:0]  = step / 100;          // 步数百位及以上（0~31）
assign dpy1       = seg7((step % 100) / 10);   // 十位
assign dpy0       = seg7(step % 10);           // 个位
```

**步数显示容量**：`LED[4:0]` 最大 31，数码管最大 99 → **31×100+99 = 3199 步**。超出时饱和在 3199（`LED[4:0]=31`、数码管 `99`）。

**数码管段码位序（非标准，必须记清）**：来自顶层注释

```
p=dpy0[0]  // 小数点      b=dpy0[4]
c=dpy0[1]                 a=dpy0[5]
d=dpy0[2]                 f=dpy0[6]
e=dpy0[3]                 g=dpy0[7]
```

即 `dpy0 = { g, f, a, b, e, d, c, p }`（MSB→LSB）。据此推出的段码表（1 点亮）：

| 数字  | 段码     | 数字  | 段码     |
| ----- | -------- | ----- | -------- |
| `0` | `0x7E` | `5` | `0xE6` |
| `1` | `0x12` | `6` | `0xEE` |
| `2` | `0xBC` | `7` | `0x32` |
| `3` | `0xB6` | `8` | `0xFE` |
| `4` | `0xD2` | `9` | `0xF6` |

> 常见开发板用的是 `{dp,g,f,e,d,c,b,a}`，**直接照抄会整屏乱码**。

**按键输入三级处理**（缺一不可）：

```
touch_btn[n] ──► [两级同步器] ──► [边沿检测] ──► 单拍脉冲 → BTN 寄存器
                  (clk_sys)          (异或后寄存)
```

1. **两级同步器**：按钮是异步输入，直接进状态机会亚稳态；
2. **边沿检测**：软件需要的是"按下了"这个**事件**而非电平，单拍脉冲天然实现"长按只算一次"；
3. **读后清除**：软件读 `BTN` 后硬件清零，保证一次按下只被消费一次。

> 顶层注释说明按钮带**硬件消抖电路**，FPGA 侧不需再计数消抖。

**计时器与随机源**（两个自由运行计数器，是 2048 与 AI 的必要基础设施）：

```verilog
// 毫秒计时：50 MHz / 50 000 = 1 kHz
reg [15:0] div;  reg [31:0] ms_cnt;
always @(posedge clk_sys) begin
    if (rst_sys) begin div <= 0; ms_cnt <= 0; end
    else if (div == 16'd49_999) begin div <= 0; ms_cnt <= ms_cnt + 1; end
    else div <= div + 1;
end

// 随机源：50 MHz 自由计数
reg [31:0] raw_cnt;
always @(posedge clk_sys) raw_cnt <= rst_sys ? 0 : raw_cnt + 1;
```

- `TIME`：AI 迭代加深的时间预算、渲染耗时统计；
- `RAND`：2048 随机方块生成。**没有它每局棋盘的随机序列完全相同，演示完全失效**——这是必须存在的计数器。

#### 2.2.7 DVI 子系统

**DVI 与 CPU 完全解耦**：它不在总线上，只有一个读端口接 ExtRAM、**两根单比特控制线**与 confreg 相连。

```
  ExtRAM ─────────────────►┌──────────────────────────────────────┐
   (read master)           │ 地址生成 → 4px 打包 → 行 FIFO → RGB332 │
                           └───▲──────────────┬───────────────────┘
                               │              │
                    fb_sel ────┘              │  vsync_start
                 （基址选择）                  ▼  （消隐期起点脉冲）
                                          ┌──────────┐
                                          │ confreg  │  ← 拥有 fb_sel 与 flip_req 两个寄存器
                                          └──────────┘
```

**关键分工**：`fb_sel` 与 `flip_req` **两个寄存器都实现在 confreg 里**，DVI 只输出一根 `vsync_start` 脉冲。DVI 自身**没有任何双缓冲状态**。

##### 2.2.7.1 时序发生器

本质是**两个自由运行计数器 + 阈值比较**。参数取自官方演示并已验证：

| 参数                      | 值             | 参数                      | 值            |
| ------------------------- | -------------- | ------------------------- | ------------- |
| 行有效 `H_ACTIVE`       | 800            | 场有效 `V_ACTIVE`       | 600           |
| 行同步起 `H_SYNC_START` | 856            | 场同步起 `V_SYNC_START` | 637           |
| 行同步止 `H_SYNC_END`   | 976            | 场同步止 `V_SYNC_END`   | 643           |
| 行总长 `H_TOTAL`        | **1040** | 场总长 `V_TOTAL`        | **666** |

```verilog
always @(posedge clk_sys) begin
    if (rst_sys) begin hcnt <= 0; vcnt <= 0; end
    else if (hcnt == H_TOTAL-1) begin
        hcnt <= 0;
        vcnt <= (vcnt == V_TOTAL-1) ? 0 : vcnt + 1;
    end else hcnt <= hcnt + 1;
end
assign video_hsync = (hcnt >= H_SYNC_START) && (hcnt < H_SYNC_END);  // 正极性
assign video_vsync = (vcnt >= V_SYNC_START) && (vcnt < V_SYNC_END);
assign video_de    = (hcnt < H_ACTIVE) && (vcnt < V_ACTIVE);
```

**刷新率** = 50 000 000 / (1040 × 666) = **72.19 Hz**。

**为什么用计数器而非状态机**：视频时序是严格等间隔的，计数器天然保证每帧恒定 1040×666 拍、永不漂移；状态机容易在前后沿交界写错。

##### 2.2.7.2 帧缓冲读出：4 像素打包

**问题**：像素 1 字节/像素，若逐像素读 SRAM，需 50 M 次读/秒 → **占满整条 ExtRAM 总线**，CPU 无法绘制。

**解法**：SRAM 是 32 位宽，一次读出 4 个像素，写入 FIFO 后逐像素吐出。

| 指标                | 数值                 |
| ------------------- | -------------------- |
| 每行有效像素        | 800                  |
| 每次读出的像素数    | 4                    |
| 每行读次数          | **200 字**     |
| 每帧读次数          | **120 000 字** |
| 占 50 M 字/s 的比例 | **17.3%**      |

相比逐像素读的 100%，**节省 83% 带宽**。

**FIFO 深度取 2 行（2 × 800 B = 1600 B）**：

- 深 1 行在行边界必然下溢（本行读完才能读下一行）；
- 深 2 行可乒乓预取，显示第 n 行时读第 n+1 行，**彻底消除行边界抖动**；
- 1600 B 在 BRAM 中不到 2 个 36 Kb block。

##### 2.2.7.3 双缓冲与 VSYNC 原子翻页

**撕裂成因**：CPU 直接绘制到正在显示的帧上，显示器扫到某行时该行被改写 → 屏幕上同时出现新画面上半部 + 旧画面下半部。

**解法**：两块缓冲 + 场上同步翻页，全部由 confreg 的 `FB_CTRL` 驱动。

```
ExtRAM:
  FB0  @ 0xA000_0000  120 000 字（480 000 B）
  FB1  @ 0xA008_0000  120 000 字

CPU 永远只画 "后缓冲"，DVI 永远只读 "前缓冲"
```

**握手协议**（confreg ↔ DVI 两根单比特线）。

> **先澄清一个常见误解：`FB_CTRL` 不需要总线仲裁。**
> `FB_CTRL` 位于 confreg（`0xBFD0_0018`），而 **DVI 根本没有 CPU 地址空间的访问能力**——它只有一条固定基址的 ExtRAM 读通道。DVI 既不读也不写这个寄存器。
> 因此这里**不存在两个主机争用同一寄存器的问题**，真正的仲裁只有一处：**ExtRAM 的 CPU 与 DVI 读端口**（见 2.2.5）。

**先回答一个容易搞错的问题：`FB_CTRL[0]` 是谁清 0 的？**

> **不是 DVI 控制器清的，而是 confreg 自己的寄存器逻辑清的；DVI 只是提供了一个触发时机。**

这是刻意的分工。DVI 在这里是**纯哑扫描器**（设计原则 2.2.7 的"极简"要求）：它只负责"按 `fb_sel` 选定的基址把像素扫出来"，**不持有任何双缓冲状态，也不知道翻页这回事**。缓冲策略属于系统/软件层，归 confreg。

因此实际只有 **2 根线**：

| 信号            | 方向                     | 含义                                                             |
| --------------- | ------------------------ | ---------------------------------------------------------------- |
| `vsync_start` | **DVI → confreg** | 进入垂直消隐区的那一拍脉冲，即 `(hcnt==0) && (vcnt==V_ACTIVE)` |
| `fb_sel`      | **confreg → DVI** | 当前要扫描哪块缓冲（0=FB0, 1=FB1）                               |

`flip_req` **是 confreg 内部的寄存器，从不离开 confreg**。之前若有"flip_req 送给 DVI"的印象，那是画错了：DVI 拿到 `flip_req` 也没用，它没有能力改 `fb_sel`。

**由此带来的存储侧副作用**：`fb_sel` 在 confreg 里翻转后组合地接到 DVI 的地址生成器，所以 **DVI 必须在下降沿就能看到新基址**——同一时钟域，无延迟问题。

**接着说必须处理的真问题：字段所有权。**
`FB_CTRL` 里面有 **两个归属不同的字段**：

| 位       | 字段                         | 写者                                                                         | 读者     |
| -------- | ---------------------------- | ---------------------------------------------------------------------------- | -------- |
| `[0]`  | `flip_req`（翻页请求）     | **CPU 写 1 置位**；**confreg 内部逻辑在 `vsync_start` 时清 0** | CPU 轮询 |
| `[16]` | `fb_sel`（当前显示缓冲号） | **仅在 `vsync_start` 时由 confreg 逻辑翻转**                         | CPU 只读 |

**如果 CPU 用整字写（`REG_FBCTRL = 1;`）而不做处理，会把 `bit[16]` 一起覆盖成 0**——软件读回的"当前显示缓冲号"就永远是错的，调试时会被误导。这不是仲裁问题，而是**必须把寄存器实现成"部分写"语义**：

```verilog
// —— confreg 侧：FB_CTRL 的读/写语义（两个寄存器都在这里，DVI 不参与）——
reg flip_req;      // bit[0]：CPU 可写 1 置位，confreg 逻辑在 vsync_start 时清 0
reg fb_sel;        // bit[16]：仅在 vsync_start 时由本逻辑翻转，CPU 只读

always @(posedge clk_sys) begin
    if (rst_sys) begin
        flip_req <= 1'b0;
        fb_sel   <= 1'b0;
    end else begin
        // ① 翻页：vsync_start 来自 DVI 时序发生器；翻转与清请求同一拍原子完成
        if (vsync_start && flip_req) begin
            fb_sel   <= ~fb_sel;
            flip_req <= 1'b0;
        end
        // ② CPU 写：只看 bit[0]，其余位一律忽略（关键！）
        if (wr_fbctrl)
            flip_req <= wdata[0];
    end
end

assign dvi_fb_sel   = fb_sel;                                  // 送 DVI 选基址
assign fbctrl_rdata = { 15'b0, fb_sel, 15'b0, flip_req };      // 读回
```

**要点**：

1. **CPU 写只影响 `bit[0]`**，`wdata[16]` 等其余位被丢弃，`fb_sel` 永不被软件覆盖；
2. **翻转与清请求必须同一拍**（写在同一个 `if` 分支里）。若分成两拍，软件可能读到 `flip_req=0` 但 `fb_sel` 尚未更新的中间态，于是错误地认为翻页已完成；
3. **② 的优先级高于 ①**（同一 `always` 块中后写的赋值优先）。两者同拍发生时，`fb_sel` 照常翻转、`flip_req` 被 CPU 重新置位——因为 `flip_req <= 1` 是**幂等**的，不会攒出"队列"；
4. **全程同一时钟域**（`clk_sys = clk_pix = 50 MHz`），所以这些信号**不存在亚稳态**，无需两级同步器。

**配套要求：DVI 的预取器必须在垂直消隐期停止取数并清空 FIFO。**
`fb_sel` 是一根组合信号，翻转瞬间 DVI 的地址生成器立刻看到新基址。若预取器在消隐期仍然盲目计算 `row_addr = (vcnt+1) × 800`，就会把**旧缓冲的第 0 行**取进 FIFO，导致新一帧的第一行串色。三重保护：

```verilog
// ① 预取门控：只在有效行区内取数
wire prefetch_en = (vcnt < V_ACTIVE) && (hcnt < H_ACTIVE) || (行 FIFO 见底);

// ② 翻页时 flush FIFO
wire fifo_flush = fb_sel_changed;      // fb_sel 打一拍后异或得到单拍脉冲

// ③ 读指针与地址在同一拍对齐（同域，无需握手）
assign dvi_base = fb_sel ? 32'hA008_0000 : 32'hA000_0000;
```

**软件协议是安全的前提**。流程中的"轮询到 0 才继续"保证了**同一时刻最多只有一个未完成的翻页请求**：

```
1. 画到后缓冲（全屏约 10 ms）
2. 写 FB_CTRL[0] = 1 请求翻页
3. 轮询 FB_CTRL[0] 直到变 0（confreg 已在 vsync_start 清位，最长等 14 ms）
4. 交换 back 指针，继续下一帧
```

若省掉第 3 步连续发两次请求，第二次会在**下一个** VSYNC 翻转，把刚画好的帧又翻回前缓冲、而 CPU 正往里画——撕裂就又回来了。**这一步不能省。**

**另一个隐含前提：帧缓冲写不能有写缓冲（write buffer）。**
软件的存储顺序是"先写完所有像素，再写 `FB_CTRL`"。这一正确性依赖 **SRAM 写在 2 拍内被 ack、CPU 逐条停顿**（2.2.4）。若后期为提速加了写缓冲，必须在写 `FB_CTRL` 前**强制 drain**，否则 DVI 可能在像素尚未落到 ExtRAM 时就翻转显示，屏幕上出现不完整的一帧。

**为什么在 VSYNC 期间翻**：此刻显示器正在消隐、不取像素，切换基址不会出现"半新半旧"的帧。翻转是原子的（一个寄存器），软件无需在像素级做任何同步。

第 3 步的阻塞是可接受的（回合制游戏无实时动画需求），换来的是**永不撕裂**。

##### 2.2.7.4 RGB332 像素格式与配色

像素字节与输出端口一一对应：

```
 bit7 6 5 │ 4 3 2 │ 1 0
 ┌────────┼───────┼─────┐
 │ R[2:0] │ G[2:0]│B[1:0]│
 └────────┴───────┴─────┘
      │        │      │
 video_red video_green video_blue
```

**本设计只需 3 种颜色**（因为不区分不同数值的色块，且无其它 UI），RGB332 的低色深完全够用：

| 用途        | 值       | 实际 RGB888             |
| ----------- | -------- | ----------------------- |
| 背景 / 空格 | `0x6D` | R96 G96 B64（中灰暖调） |
| 数字块底色  | `0xEF` | R224 G224 B192（米白）  |
| 数字前景    | `0x00` | 纯黑                    |

**这是本设计相比"按数值上色"的巨大简化**：原版 2048 的米色渐变在 RGB332 下会大量撞色（`#EEE4DA` 与 `#FAF8EF` 都量化为 `0xFF`，方块会消失）；而三色方案中三者亮度差 ≥ 3 级，**肉眼分辨毫无问题**。

> 若后期想恢复按值上色，需重新标定 12~14 级调色板并做量化预览验证。

##### 2.2.7.5 像素时钟输出

演示代码用 `assign video_clk = clk_50M` 直接前向时钟。若上板后出现**像素抖动、雪花、边缘闪烁**，改用 ODDR 降低输出抖动：

```verilog
ODDR #(.DDR_CLK_EDGE("SAME_EDGE"), .INIT(1'b0), .SRTYPE("SYNC"))
  u_pixclk (.Q(video_clk), .C(clk_sys), .CE(1'b1),
            .D1(1'b1), .D2(1'b0), .R(1'b0), .S(1'b0));
```

#### 2.2.8 时序约束与资源

| 路径                           | 处理                                                                                                                                    |
| ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------- |
| PLL 生成时钟                   | IP 自动处理                                                                                                                             |
| `base_ram_*` / `ext_ram_*` | **必须设 `set_output_delay` / `set_input_delay`**（相对 `clk_sys`，按 10 ns 器件建立/保持），否则报告会出现虚假的无限 slack |
| `video_*` 输出               | 可 `set_false_path`（板载发送器按自身时钟采样，无跨器件同步关系）                                                                     |
| `touch_btn` / `dip_sw`     | 可不设 input delay（异步输入），但**必须保留两级同步器**                                                                          |
| 像素 FIFO                      | 用 BRAM 原语，别被综合成分布式 RAM                                                                                                      |

**收敛目标**：`clk_sys = 50 MHz` 下 **WNS ≥ 1.0 ns、TNS = 0、无 unsatisfied path**。

**资源估算（XC7A200T-2FBG676C）**：

| 资源         | 总量     | 估算            | 占比 |
| ------------ | -------- | --------------- | ---- |
| LUT          | ~134 600 | 8 000 ~ 15 000  | ~10% |
| FF           | ~269 200 | 10 000 ~ 20 000 | ~7%  |
| BRAM (36 Kb) | 365      | 10 ~ 30         | ~8%  |
| DSP48E1      | 740      | 0               | 0%   |

资源非常宽裕，唯一要盯的是**时序**与**BaseRAM 带宽**。

### 2.3 软件实现

#### 2.3.1 内存布局与链接脚本

以下为早期方案示例。已验证的当前布局见 [sw/boot/link.ld](../sw/boot/link.ld)：BaseRAM 起点 `0x1C000000`、栈顶 `0x1C400000`、16 KiB 预留栈，data 通过 LMA/VMA 搬移初始化。

```
0x8000_0000  ┌──────────────────────────┐
             │ .text    (代码)           │
             ├──────────────────────────┤
             │ .rodata  (字模 10×16 B)   │  ← 只需数字 0-9，共 160 B
0x8010_0000  ├──────────────────────────┤
             │ .data    (已初始化数据)    │
             ├──────────────────────────┤
             │ .bss     (清零数据)       │
             ├──────────────────────────┤
             │ heap     (不使用 malloc)  │
0x8040_0000  ├──────────────────────────┤
             │ stack    (向下增长)        │  ← sp 初始化于此
0x8040_0000  └──────────────────────────┘
```

```ld
MEMORY { RAM (rwx) : ORIGIN = 0x80000000, LENGTH = 4M }
ENTRY(_start)
SECTIONS {
    . = 0x80000000;
    .text   : { *(.text.start) *(.text*) }
    .rodata : { *(.rodata*) *(.srodata*) }
    . = ALIGN(4);
    _data_start = .;
    .data   : { *(.data*) *(.sdata*) }
    _data_end = .;
    _bss_start = .;
    .bss    : { *(.bss*) *(.sbss*) *(COMMON) }
    _bss_end = .;
    _stack_top = 0x80400000;
}
```

**不用 `malloc`**：裸机无 MMU，动态分配只带来碎片与不确定延迟。全部静态分配；AI 大表用 `static` 数组直接落 `.bss`（因 AI 表放 ExtRAM，用 `__attribute__((section(".extram")))` 或绝对地址宏）。

**栈溢出防护**：栈向下增长会侵入 `.bss`，是裸机最难查的 bug。在 `_stack_top - 16` 放金丝雀 `0xDEADBEEF`，主循环定期检查。

#### 2.3.2 启动流程（`crt0.S`）

以下为早期流程示意。当前 [crt0.S](../sw/boot/crt0.S) 实际顺序为设置栈、搬移 data、清零 BSS、调用 main、返回后停机循环，入口和结果见本节顶部的实施状态。

```
上电 / reset_btn
  ├─ 1. 跳转 _start（.text.start 链接在最前，地址 0x8000_0000）
  ├─ 2. 设置 sp = _stack_top
  ├─ 3. 清零 .bss（_bss_start → _bss_end）
  ├─ 4. 搬运 .data（若 LMA 在别处）
  ├─ 5. bl main
  └─ 6. main 返回则死循环
```

**`.bss` 清零必须在任何 C 函数调用之前完成**，否则静态变量初值不确定。若把 AI 大表放进未清零区域，会变成垃圾数据——**这是最容易翻车的一步**。

**镜像下载**：不使用 NOR Flash 与自启动，直接经 **JTAG 把 elf/bin 写入 SRAM** 后释放复位。简化了 Flash 控制器与 bootloader，代价是每次上电需重新下载（现场演示前需预热确认）。

#### 2.3.4 驱动层

##### confreg 驱动 `drv/confreg.c`

```c
#define CONF_BASE   0xBFD00000
#define REG_STEP    (*(volatile uint32_t*)(CONF_BASE + 0x00))
#define REG_STATUS  (*(volatile uint32_t*)(CONF_BASE + 0x04))
#define REG_BTN     (*(volatile uint32_t*)(CONF_BASE + 0x08))
#define REG_KEY     (*(volatile uint32_t*)(CONF_BASE + 0x0C))
#define REG_TIME    (*(volatile uint32_t*)(CONF_BASE + 0x10))
#define REG_RAND    (*(volatile uint32_t*)(CONF_BASE + 0x14))
#define REG_FBCTRL  (*(volatile uint32_t*)(CONF_BASE + 0x18))

static inline uint32_t time_ms(void) { return REG_TIME; }
static inline uint32_t rand_raw(void){ return REG_RAND; }
static inline uint8_t  btn_poll(void){ return REG_BTN & 0xF; }  /* 读即清 */
static inline uint8_t  key_read(void){ return REG_KEY & 0x3; }
```

**随机数生成**：不能直接把 `RAND` 当随机数（相邻两次读只差几十，游戏性很差）。用 xorshift32，种子取 `RAND`：

```c
static uint32_t rng_state;
void rng_seed(void) { rng_state = rand_raw() | 1u; }   /* 保证非零 */

uint32_t rng_next(void) {
    uint32_t x = rng_state;
    x ^= x << 13;  x ^= x >> 17;  x ^= x << 5;
    return rng_state = x;
}
```

**为什么必须 seed**：若用固定种子，每局随机序列完全相同，AI 面对相同局面永远走同一路线，**演示与回归测试都会失去意义**。

##### 帧缓冲驱动 `drv/fb.c`

```c
#define FB0_BASE  0xA0000000u
#define FB1_BASE  0xA0080000u
#define PITCH     800            /* 字节/行 */
#define SCREEN_W  800
#define SCREEN_H  600

static uint32_t fb_back;         /* 当前后缓冲基址 */

void fb_begin_frame(void) { /* 无操作，保持 fb_back */ }

void fb_end_frame(void) {
    REG_FBCTRL = 1;                        /* 请求翻页 */
    while (REG_FBCTRL & 1) ;               /* 等 VSYNC 接受，最长 14 ms */
    fb_back = (fb_back == FB0_BASE) ? FB1_BASE : FB0_BASE;
}

void fb_fill_rect(int x, int y, int w, int h, uint8_t c) {
    uint32_t px4 = (uint32_t)c * 0x01010101u;     /* 4 个相同像素打包 */
    uint32_t *row = (uint32_t*)(fb_back + y * PITCH + x);
    for (int j = 0; j < h; j++, row += PITCH / 4)
        for (int i = 0; i < w / 4; i++)
            row[i] = px4;                         /* 一次写 4 像素 */
    /* 尾部 w % 4 像素逐字节写 */
}
```

**对齐铁律（LA32R 特有）**：`fb_fill_rect` 用 32 位写，因此 **`x` 必须是 4 的倍数、`w` 应为 4 的倍数**。x86 上非对齐写只是慢一点，**LA32R 上直接触发地址错异常**。本节所有绘制坐标都已按此设计（见 2.3.5）。

`PITCH = 800` 是 4 的倍数，所以行首地址天然对齐，**只要 `x` 对齐即可**。

##### 输入驱动 `drv/kbd.c`

```c
#define BTN_UP    0x1
#define BTN_DOWN  0x2
#define BTN_LEFT  0x4
#define BTN_RIGHT 0x8

/* 按键位映射：BTN1/btn[0]=上 BTN2/btn[1]=下 BTN3/btn[2]=左 BTN4/btn[3]=右 */
```

按键事件直接来自 `confreg` 的单拍脉冲，无需软件消抖。

当前方向位映射为 BTN1/bit0=上、BTN2/bit1=下、BTN3/bit2=左、BTN4/bit3=右。多键同时置位时，软件按上、左、下、右优先序消费，对应掩码顺序为 `1, 4, 2, 8`。

#### 2.3.5 界面布局与配色

**屏幕 800×600 被 4×4 网格完全铺满**（无标题栏、无分数、无状态行）：

| 项                       | 值                                                            |
| ------------------------ | ------------------------------------------------------------- |
| 单元格尺寸               | **200 × 150**                                          |
| 网格原点                 | `(0, 0)`，铺满全屏                                          |
| 单元格 `(r, c)` 左上角 | `x = c × 200`，`y = r × 150`                            |
| 方块内缩                 | **8 px**（四边）                                        |
| 方块实际尺寸             | **184 × 134**，左上角 `(c × 200 + 8, r × 150 + 8)` |

**绘制顺序**：

```
1. 整屏填充 0x6D（背景/网格底色）          —— 空格最终就是这个色
2. 对每个非空格：填 0xEF 的 184×134 矩形
3. 对每个非空格：在其上居中绘制数字（0x00）
```

**为什么 x 方向全部对齐**：`c×200` 是 4 的倍数；`+8` 后仍是 4 的倍数；宽度 184 是 4 的倍数 ✓。`y` 不受对齐约束（因 `PITCH` 是 4 的倍数）。

**数字居中偏移计算**（字模放大 3× = 每字符 24 px 宽、48 px 高）：

| 位数                     | 文本宽 | x 内偏移          | 最终 x          | 4 对齐 |
| ------------------------ | ------ | ----------------- | --------------- | ------ |
| 1（`2`~`8`）         | 24     | (184−24)/2 = 80  | `c×200 + 88` | ✓     |
| 2（`16`~`64`）       | 48     | (184−48)/2 = 68  | `c×200 + 76` | ✓     |
| 3（`128`~`512`）     | 72     | (184−72)/2 = 56  | `c×200 + 64` | ✓     |
| 4（`1024`~`8192`）   | 96     | (184−96)/2 = 44  | `c×200 + 52` | ✓     |
| 5（`16384`~`65536`） | 120    | (184−120)/2 = 32 | `c×200 + 40` | ✓     |

竖直方向统一：`y = r × 150 + 8 + 43 = r × 150 + 51`。

**字号统一用 3×**（不随位数变化）：5 位数 120 px < 184 px 可用宽度，**一套字号覆盖所有情况**，代码最简单。

#### 2.3.6 位图字体与数字渲染

**字模规格**：`8 × 16` 点阵，每字 **16 字节**（每字节 1 行，bit7 在最左）。

**字符集只需 `0`~`9` 十个** —— 因为界面上不显示任何文字（无 SCORE/BEST/AI 标签）。总容量 **160 字节**，放 `.rodata` 或 BRAM 均可。

**放大 3× 的渲染**：

```c
void fb_blit_glyph(int x, int y, const uint8_t g[16], uint8_t fg, int scale) {
    for (int row = 0; row < 16; row++) {
        uint8_t bits = g[row];
        for (int col = 0; col < 8; col++) {
            if (!(bits & (0x80 >> col))) continue;      /* 只画亮点 */
            uint8_t *p = FB(fb_back, x + col*scale, y + row*scale);
            for (int dy = 0; dy < scale; dy++)          /* scale×scale 方块 */
                for (int dx = 0; dx < scale; dx++)
                    p[dy*PITCH + dx] = fg;
        }
    }
}
```

**只写亮的像素**，背景已由矩形填充完成，因此每个数字约需写 1 800 字节，**远少于全矩形填充**。

**性能估算**：

| 操作               | 写入字节               | 32 位写次数 | 估算耗时           |
| ------------------ | ---------------------- | ----------- | ------------------ |
| 整屏清为 0x6D      | 480 000                | 120 000     | ≈ 4.8 ms          |
| 16 个非空块填充    | 16 × 24 656 = 394 496 | 98 624      | ≈ 4.0 ms          |
| 数字绘制（16 块）  | ≈ 29 000（字节写）    | —          | ≈ 1.2 ms          |
| **单帧合计** |                        |             | **≈ 10 ms** |

一帧 13.85 ms，重绘 10 ms，**刚好放得下**。若后期需要余量，改为"只重绘变化格"可降到 ~2 ms。

#### 2.3.7 2048 规则内核

##### 数据结构

```c
typedef struct {
    uint8_t  cell[16];   /* 4 bit/格：0=空，k=2^k 方块（1..15） */
    uint32_t score;      /* 分数（不显示，仅供内部与答辩报数） */
    uint32_t steps;      /* 有效移动次数（显示在数码管+LED） */
    uint8_t  state;      /* PLAYING / WIN / LOSE */
} game_t;
```

**用指数而非数值**：`uint8_t` 足够表达 2~32768；合并判定只需"指数相等"；渲染时可查表由指数得位数与是否胜利。

##### 移动/合并算法（正确性核心）

标准三步法，顺序不可颠倒：

```
对每一行（按方向统一到"向索引 0 平移"）：

第 1 步 压缩：非零元素按序前移
第 2 步 合并：从左扫描，相邻相等则合并（指数+1），
             分数 += 2^(新指数)，
             索引跳过 2 位 ← 关键，防止 [2,2,2,2] 变成 [8,0,0,0]
第 3 步 再压缩：合并产生的空洞再次前移
```

**四方向统一化**（代码量减 4 倍）：

```
向左 = 直接调用 move_row_left()
向右 = 每行反转 → 向左 → 再反转
向上 = 转置 → 向左
向下 = 转置 → 向右
```

只需实现 `move_row_left(uint8_t r[4])` 一个函数，其余通过索引映射复用。

##### 随机方块生成

```c
int spawn_tile(game_t *g) {
    int empty[16], n = 0;
    for (int i = 0; i < 16; i++) if (!g->cell[i]) empty[n++] = i;
    if (!n) return 0;

    uint32_t r = rng_next();
    g->cell[empty[r % n]] = ((r >> 8) % 10 == 0) ? 2 : 1;   /* 90% 出 2，10% 出 4 */
    return 1;
}
```

原版概率为 90% 出 2 / 10% 出 4。取模偏差（2³² 不是 10 的倍数）在此量级完全无影响。

##### 胜负判定

```c
/* 胜利：任一格达到 2048（指数 11） */
int check_win(const game_t *g) {
    for (int i = 0; i < 16; i++) if (g->cell[i] >= 11) return 1;
    return 0;
}

/* 失败：无空格 且 无相邻相等（则任何方向都动不了） */
int check_lose(const game_t *g) {
    for (int i = 0; i < 16; i++) {
        if (!g->cell[i]) return 0;                              /* 还有空格 */
        if (i % 4 != 3 && g->cell[i] == g->cell[i+1]) return 0; /* 行相邻相等 */
        if (i < 12     && g->cell[i] == g->cell[i+4]) return 0; /* 列相邻相等 */
    }
    return 1;
}
```

#### 2.3.8 主循环与状态机

##### 状态机

```
                    key[0] 0→1 上升沿（重开，不保存旧局）
                              │
                              ▼
      ┌───────────────────────────────────────┐
      │              PLAYING                  │
      │  key[1]=0 → 手动：btn[3:0] 驱动移动    │
      │  key[1]=1 → AI  ：见第 3 章            │
      └──────┬─────────────────────┬──────────┘
             │ 出现 2048           │ 无可动方向
             ▼                     ▼
      ┌────────────┐        ┌────────────┐
      │    WIN     │        │    LOSE    │
      │ LED[13]=1  │        │ LED[14]=1  │
      │ DVI 冻结   │        │ DVI 冻结   │
      │ CPU 死循环 │        │ CPU 死循环 │
      └─────┬──────┘        └─────┬──────┘
            └────────┬────────────┘
                     │ 等待 key[0]：先见 0，再见 1
                     └──────────► PLAYING（新局）
```

##### 结束后的确定性行为（严格按规格）

```c
if (g.state != PLAYING) {
    P->status_show(status_bits);         /* LED[15:13] 置位 */
    P->step_show(g.steps);               /* 冻结步数显示 */
    /* DVI 不再更新：不写帧缓冲、不调用 fb_end_frame */
    for (;;) {
        while (P->key_read() & 0x1) ;    /* 阶段一：等 key[0] 变 0 */
        while (!(P->key_read() & 0x1)) ; /* 阶段二：等 key[0] 变 1（上升沿） */
        game_new();                      /* 重开新局，不保存旧局 */
        break;
    }
}
```

**注意两点**：

1. **必须两阶段等待**。失败时 `key[0]` 仍为 1，只检测上升沿会立刻误触发，必须"先见到 0 再见到 1"。
2. **DVI 冻结**：结束后完全不触碰帧缓冲与 `FB_CTRL`，屏幕上保留最后一帧，玩家通过 `LED[14]`/`LED[13]` 判断结果。

##### 主循环

```c
void game_run(void) {
    if (P->key_read() & 0x1) { /* 已在运行位置 */ }
    game_new();                                  /* 上电后等 key[0] */

    for (;;) {
        if (!(P->key_read() & 0x1)) {            /* key[0]=0：游戏关闭 */
            while (!(P->key_read() & 0x1)) ;     /* 等待重新打开 */
            game_new();                          /* 上升沿：重开 */
        }

        int ai_mode = (P->key_read() >> 1) & 1;
        P->status_show((ai_mode ? 0x8000 : 0) | status_flags);

        int moved = 0;
        if (!ai_mode) {
            uint8_t ev = P->btn_poll();
            if (ev) moved = game_try_move(&g, ev_to_dir(ev));
        } else {
            moved = ai_step(&g);                 /* 见 3.4 */
        }

        if (moved) {
            g.steps++;
            P->step_show(g.steps);               /* 数码管 + LED[4:0] */
            view_draw(&g);                       /* 整屏重绘到后缓冲 */
            P->fb_end_frame();                   /* 请求翻页并等待 VSYNC */
        }

        if (check_win(&g))  { g.state = WIN;  loop_forever(); }
        if (check_lose(&g)) { g.state = LOSE; loop_forever(); }
    }
}
```

**关键设计点**：**只有 `moved` 为真时才重绘**。2048 是回合制，非法方向（棋盘无变化）不产生任何视觉变化，此时跳过重绘可省下 10 ms。这使静止时 CPU 占用接近 0。

**步数语义**：只统计**棋盘真正发生变化的有效移动**；非法方向按键不计。这也是 AI 的思考次数。

#### 2.3.9 板载反馈：数码管与 LED 分配

**数码管**：`dpy1`=步数十位，`dpy0`=步数个位，显示 `step % 100`（00~99）。

**LED 分配**（16 位全用完）：

| LED        | 含义                                             | 来源             |
| ---------- | ------------------------------------------------ | ---------------- |
| `[15]`   | **AI 模式**（`key[1]`=1 时亮）           | `STATUS[15]`   |
| `[14]`   | **游戏失败**                               | `STATUS[14]`   |
| `[13]`   | **游戏胜利**（合出 2048）                  | `STATUS[13]`   |
| `[12:9]` | 调试：AI 最近一次搜索深度（0~8）                 | `STATUS[12:9]` |
| `[8:5]`  | 调试：上一帧渲染耗时 ÷ 2 ms（饱和 31 → 62 ms） | `STATUS[8:5]`  |
| `[4:0]`  | **步数百位及以上**（0~31）                 | `STEP ÷ 100`  |

**步数显示能力**：`31 × 100 + 99 = 3199` 步。超出时饱和显示 `LED[4:0]=31`、数码管 `99`。

> 真实 2048 对局打到 2048 通常需 1500~2500 步，3199 的上限有余量。

**`[15]`/`[14]`/`[13]` 三位的现场诊断价值**：

- LED[15] 亮但画面不动 → AI 在搜索（正常）；
- LED[14] 亮 → 失败，等 key[0]；
- LED[13] 亮 → 胜利；
- 三位全灭但画面不动 → 程序卡死，看 LED[8:5] 判断是渲染慢还是死循环。

## 3. 目标二：Expectimax AI

### 3.1 目标定义与验收标准

| 项               | 内容                                                                                                                                                         |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **入口**   | `key[1]` 拨到 1 → AI 接管；拨回 0 → 手动                                                                                                                 |
| **接管点** | **任意当前局面**（手动玩到一半直接拨过去）或初始新局                                                                                                   |
| **验收**   | ① AI 自动游玩，屏幕持续更新 ② 连续 5 局平均分 ≥ 10000、最高块 ≥ 1024 ③ 至少 1 局到达 2048（`LED[13]` 亮）④ 单步耗时 ≤ 300 ms ⑤ 手动↔AI 切换无异常 |

**本目标不新增任何 RTL**。AI 完全运行在 LA32R 软件层，复用目标一的全部外设。

### 3.2 硬件复用与 AI 数据表放置

AI 需要两块大表，**都放在 ExtRAM**（而非 BaseRAM）：

| 表                                   | 大小   | 地址            |
| ------------------------------------ | ------ | --------------- |
| `next_row[65536]`（`uint16_t`）  | 128 KB | `0xA010_0000` |
| `row_score[65536]`（`uint32_t`） | 256 KB | `0xA012_0000` |
| 转置表 `2^16 × 8 B`               | 512 KB | `0xA018_0000` |

**为什么放 ExtRAM**：BaseRAM 要同时承受取指与访存，是最紧张的通道（>100% 需求）；ExtRAM 除 DVI 扫描（17.3%）外几乎空闲。把 896 KB 的大表搬过去，等于把负载从瓶颈挪到空地。搬完后 ExtRAM 占用约 46%，BaseRAM 仅约 6%。

**`row_score` 必须 32 位**：一行 4 格极端情况下合并得分可达 2¹⁸，`uint16_t` 会溢出。

### 3.3 算法原理

#### 3.3.1 2048 是随机单人博弈，不能用 Minimax

2048 不是零和博弈：对手是"随机放置方块"这个**自然过程**。因此搜索树是两类节点交替：

- **玩家节点（max）**：从 4 个方向中选一个 → 取 `max`
- **随机节点（expectation）**：在随机空位生成 2 或 4 → 取**数学期望** `E`

$$
V(s) = \max_{a \in A} \sum_{c \in \text{empty}(s_a)} \sum_{t \in \{2,4\}} p(c)\,p(t)\, V(s_a \oplus c \oplus t)
$$

其中 $s_a$ = 执行动作 $a$ 后的局面，$p(t{=}2)=0.9$、$p(t{=}4)=0.1$、$p(c)=1/|\text{empty}|$。

**终止**：到达深度上限或概率低于阈值时，返回启发式评估 $h(s)$。

#### 3.3.2 搜索规模与剪枝必要性

| 深度（层）     | 分支因子     | 未剪枝节点数 |
| -------------- | ------------ | ------------ |
| 1（玩家+随机） | 4 → 最多 32 | ≈ 10²      |
| 2              |              | ≈ 10⁴      |
| 3              |              | ≈ 10⁶      |
| 4              |              | ≈ 10⁸ ❌   |

固定深度 3 已超出 50 MHz 单发射 CPU 能力。**三条剪枝必须全上**：概率剪枝、转置表、深度限制。

#### 3.3.3 棋盘表示与行移动查表（性能命门）

**棋盘表示**（避开 64 位运算）：

```c
typedef struct { uint32_t row[4]; } board_t;
/* 每行仅用低 16 位： [15:12]=格3 [11:8]=格2 [7:4]=格1 [3:0]=格0 */
/* 格内为指数：0=空，k=2^k */
```

**查表**：把"一行 4 个 nibble"合成为 16 位索引，查预先算好的结果表：

```c
extern uint16_t next_row[65536];    /* ExtRAM @ 0xA010_0000，左移一行的结果 */
extern uint32_t row_score[65536];   /* ExtRAM @ 0xA012_0000，左移得分 */
```

一次行移动从"4 次迭代 + 多次比较"降为 **4 次查表 + 3 次或运算**，指令数降一个数量级。这是 ovolve 原版思路，移植后同样有效。

**生成算法**（PC 端预生成 → 打包进镜像 → 启动时 `memcpy` 到 ExtRAM，约 3 ms）：

```c
static uint16_t apply_move_left(uint16_t idx, uint32_t *score) {
    uint8_t r[4] = { idx & 0xF, (idx>>4) & 0xF, (idx>>8) & 0xF, (idx>>12) & 0xF };
    uint8_t out[4] = {0}; int n = 0; *score = 0;
    for (int i = 0; i < 4; i++) if (r[i]) out[n++] = r[i];        /* 1. 压缩 */
    for (int i = 0; i < n - 1; ) {                               /* 2. 合并，跳 2 位 */
        if (out[i] == out[i+1]) {
            out[i]++; *score += (1u << out[i]);
            for (int j = i+1; j < n-1; j++) out[j] = out[j+1];
            out[--n] = 0;
            i++;
        } else i++;
    }
    uint8_t fin[4] = {0}; int m = 0;                             /* 3. 再压缩 */
    for (int i = 0; i < n; i++) if (out[i]) fin[m++] = out[i];
    return fin[0] | (fin[1]<<4) | (fin[2]<<8) | (fin[3]<<12);
}
```

> **PC 预生成的好处**：板上与 PC oracle 用**同一份表**，天然保证行移动语义一致，为 3.6 的一致性验证提供免费保障。

**四个方向**：只需 `left` + 反转（得 `right`）+ 转置（得上下）。4×4 nibble 转置用掩码与移位完成，无循环。

#### 3.3.4 启发式函数与整数化

| 维度                        | 含义                          | 为什么重要                   |
| --------------------------- | ----------------------------- | ---------------------------- |
| **空格数** `empty`  | 空位数量                      | 空格是最宝贵资源，少了没退路 |
| **单调性** `mono`   | 4 行 4 列是否沿某方向单调     | 单调排布才能把大块推到角落   |
| **平滑性** `smooth` | 相邻格 log₂ 差值之和（取负） | 相邻数值接近才容易合并       |
| **最大块** `maxv`   | log₂ 最大块                  | 鼓励养大最大块               |

$$
h = w_s \cdot \text{smooth} + w_m \cdot \text{mono} + w_e \cdot \text{empty} + w_v \cdot \log_2(\max)
$$

**整数化（×256 定点）**：

```c
#define W_SMOOTH   26    /* 0.1  × 256 */
#define W_MONO    256    /* 1.0  × 256 */
#define W_EMPTY   691    /* 2.7  × 256 */
#define W_MAXV    256    /* 1.0  × 256 */

static int32_t heuristic(const board_t *b) {
    return W_SMOOTH * smoothness(b)
         + W_MONO   * monotonicity(b)
         + W_EMPTY  * empty_count(b) * 256
         + W_MAXV   * max_exp(b) * 256;
}
```

**量级检查（防溢出）**：`empty` ≤ 16 → 11 056；`mono` 约 ≤ 256 → 65 536；总和在 10⁵~10⁶ 量级，**`int32_t` 安全**。

原版权重为参考值，需在 PC 上重新标定（T2.3）。

#### 3.3.5 转置表

```c
typedef struct { uint32_t key; int32_t score; } tt_entry_t;   /* 8 B */
extern tt_entry_t tt[1 << 16];                                /* ExtRAM @ 0xA018_0000，512 KB */

static inline uint32_t board_hash(const board_t *b) {
    return (b->row[0] * 0x9E3779B1u) ^ (b->row[1] * 0x85EBCA77u)
         ^ (b->row[2] * 0xC2B2AE3Du) ^ (b->row[3] * 0x27D4EB2Fu);
}
```

**直接映射 + 冲突直接覆盖**（`idx = hash & 0xFFFF`）：

- 搜索是深度优先 + 时间预算，旧条目价值本就在衰减；
- 无链表 → 无指针追逐 → 对无 Cache 的裸核更友好（一次 SRAM 读即可）。

**必须校验 `key`**：命中条件为 `tt[idx].key == hash`，否则哈希冲突会返回错误评估值。

#### 3.3.6 概率剪枝

从根累积的概率 `prob`，**根为 `65536`（Q16 定点，即 1.0 = 65536）**：

- 随机节点出 2（概率 0.9）：`prob = prob * 9 / 10 / empty_cnt`
- 随机节点出 4（概率 0.1）：`prob = prob * 1 / 10 / empty_cnt`

```c
#define PROB_ROOT       65536u   /* 1.0 */
#define PROB_THRESHOLD  6u       /* ≈ 9.2e-5，与 ovolve 的 1e-4 同量级 */

if (prob < PROB_THRESHOLD) return heuristic(b);
```

**为什么必须用 Q16 而不是 Q8**（这是易错点，务必核对）：

| 定点宽度              | 根值            | 深度 1         | 深度 2        | 深度 3              | 深度 4      |
| --------------------- | --------------- | -------------- | ------------- | ------------------- | ----------- |
| Q8                    | 256             | 16             | 1             | **0（下溢）** | 0           |
| **Q16（选用）** | **65536** | **4213** | **270** | **17**        | **1** |

假设 `empty = 14`（最坏分支因子 0.9/14 ≈ 0.064）：

- Q8 在深度 3 就归零，**搜索被下溢强行截断在深度 2~3**，代码里写的深度限制形同虚设；
- Q16 能撑到深度 4，剪枝才真正由阈值控制而非整数精度控制。

**下溢兜底**：即使 Q16，深度 5 以后也会归零。因为阈值 6 远大于归零点，**递归在归零前就已返回**，不会出现"prob=0 导致整棵子树被错误跳过"的问题。若发现搜索节点数与预期严重不符，**第一嫌疑就是这里**。

#### 3.3.7 迭代加深与时间预算

**裸机上最大的风险是"AI 想太久，游戏卡死"**。结构性保证：

```c
typedef struct {
    uint32_t deadline_ms;
    int      aborted;
    uint32_t nodes;
} search_ctx_t;

static int32_t search_max(search_ctx_t *c, board_t *b, int depth, uint32_t prob) {
    c->nodes++;
    if ((c->nodes & 0x3FF) == 0 && time_ms() > c->deadline_ms) {
        c->aborted = 1;
        return heuristic(b);                  /* 立即降级为静态评估 */
    }
    if (depth <= 0 || prob < PROB_THRESHOLD) return heuristic(b);
    /* ... 展开 4 个方向取 max ... */
}

int ai_best_move(board_t *b) {
    int best = -1;
    for (int d = 2; d <= 4; d++) {             /* 迭代加深 */
        search_ctx_t c = { .deadline_ms = time_ms() + AI_BUDGET_MS };
        int cand = search_root(&c, b, d);
        if (c.aborted) break;                  /* 超时 → 保留上一轮结果 */
        best = cand;
        if (time_ms() > c.deadline_ms) break;
    }
    return best;
}
```

**迭代加深的额外收益**：深度 2 算完就返回（省时间）；时间充裕则继续加深。**任何时刻被打断都有可用答案**——这是"绝不卡死"的结构性保证，而非靠调参。

**`AI_BUDGET_MS` 建议 250 ms**（留 50 ms 余量给渲染与其它开销）。

#### 3.3.8 深度自适应

| 空格数 | 深度     | 单步节点量级 | 理由               |
| ------ | -------- | ------------ | ------------------ |
| ≥ 7   | 2        | 10³         | 局面宽松，粗算即可 |
| 4 ~ 6  | 3        | 10⁴         | 平衡点             |
| ≤ 3   | 4        | 10⁴~10⁵    | 危险局面，必须算准 |
| 0      | 直接判负 | —           | —                 |

若 `dip_sw[7:4]` 有非零值，则覆盖自适应，强制使用该深度（便于现场演示"深度 vs 成绩"对比）。

### 3.4 与游戏主循环的接入

```c
int ai_step(game_t *g) {
    /* 1. 校验 key[1] 仍为 1，否则本次不落子（玩家已切回手动） */
    if (!((P->key_read() >> 1) & 1)) return 0;

    /* 2. 转成位板 */
    board_t b; board_from_game(&b, g);

    /* 3. 搜索 */
    uint32_t t0 = time_ms();
    int dir = ai_best_move(&b);
    uint32_t dt = time_ms() - t0;

    /* 4. 更新调试 LED */
    P->status_show(status | (min(depth,8) << 9) | (min(dt/2,31) << 5));

    /* 5. 执行移动 */
    if (dir < 0) return 0;
    return game_try_move(g, dir);
}
```

**关键点**：

- **每步都重新读 `key[1]`**，玩家拨回手动后 AI 立即停手；
- **AI 模式下 `btn[3:0]` 完全闲置**（按规格）；
- AI 的思考时间计入主循环，因此两次落子间隔 = 搜索时间 + 渲染时间。若需放慢演示节奏，可在 `ai_step` 后加 `delay_ms()`。

**AI 思考期间的画面**：由于主循环是同步阻塞的，搜索期间画面静止（但 DVI 仍在正常扫描显示，不会黑屏）。这符合预期。

### 3.6 无串口条件下的验证策略

这是去掉 UART 后必须正面解决的问题。

| 层次                 | 方法                                                                                                                                                                                    |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **算法正确性** | **同源编译**：同一份 `app/ai_*.c` 在 PC 上以 `TARGET=pc` 编译（可 printf、可跑 10 万局面回归），在板上以 `TARGET=la32r` 编译。**代码相同 + 输入相同 → 结果必然相同** |
| **确定性论证** | AI 全部使用 `int32_t`/`uint32_t` 与纯整数运算，无浮点、无未定义行为、无指针地址依赖 → **平台无关**。这是编译期保证，比运行期抽样更强                                         |

| **端到端**     | 最终判据就是**屏幕上的结果**：AI 能否自动打到 1024 / 2048，以及 `LED[13]` 是否点亮                                                                                              |
| **仿真**       | Verilator 跑完整 SoC + 真实固件，可 dump 信号波形逐拍核对                                                                                                                               |

**关键词**：**用"确定性"替代"可观测性"**。既然没有 printf，就保证算法是纯粹确定性的，让 PC 上的验证结果可以完全迁移到板上。

| 目标二 · M5 | AI 性能              | `TIME` 前后差 + LED[8:5] | 单步 ≤ 300 ms，波动 <±15%              |
| 目标二 · M5 | AI 成绩              | 20 局自动游玩              | 均值 ≥10000，最高块 ≥1024，≥1 局 2048 |
| 全程         | 稳定性               | 30 min 手动 + 2 h AI       | 无花屏、无死机、无越界                   |

**两个必做的低成本高价值测试**：

1. **确定性回放**：固定 `RAND` 种子 + 固定操作序列 → 板上与 PC 棋盘逐字节比对，一次性抓出 90% 移植 bug；
2. **金丝雀哨兵**：`_stack_top - 16` 放 `0xDEADBEEF`，主循环定期检查。栈溢出是裸机最隐蔽的崩溃源，检查成本几乎为零。

## 6. 关键取舍与风险

### 6.1 已确定的关键决策

| 决策         | 选择                                                            | 理由                                              |
| ------------ | --------------------------------------------------------------- | ------------------------------------------------- |
| CPU 外设数量 | **仅 BaseRAM / ExtRAM / confreg**                         | 极简 SoC，降低集成风险                            |
| DVI 接口     | **无 CPU 总线接口**，仅 ExtRAM 读口 + 2 根 confreg 控制线 | 满足"DVI 连 ExtRAM"；同时保留双缓冲               |
| 双缓冲       | **保留**，`FB_CTRL` 在 confreg                          | 彻底消除撕裂，代价仅 1 个寄存器位                 |
| 视频模式     | **800×600@72 Hz，像素时钟 = 50 MHz**                     | 单一时钟域、零 CDC；参数官方已验证                |
| TMDS 编码    | **不在 FPGA 内做**                                        | 板载发送器已含                                    |
| 串口         | **完全不用**                                              | 输入全板载；代价是 bring-up 依赖仿真 + LED 调试位 |
| 界面         | **只画 4×4 棋盘**，无分数/标题/状态                      | 极简，且只需 10 个数字字模（160 B）               |
| 配色         | **3 色**（空格 / 方块 / 数字）                            | 不区分数值颜色，RGB332 低色深完全够用             |
| 步数显示     | 数码管 00~99 + `LED[4:0]` 高位，上限 **3199**           | 覆盖真实对局（1500~2500 步）                      |
| AI 数据表    | **放 ExtRAM**                                             | 把负载从瓶颈通道（BaseRAM）搬到空闲通道           |
| AI 算术      | **全整数定点**                                            | IP 无 FPU；且带来"同源确定性"这一验证优势         |
| AI 时间预算  | **迭代加深 + 250 ms 截止**                                | 结构性保证绝不卡死                                |
| 内存分配     | 全静态，不用 `malloc`                                         | 无碎片、延迟确定                                  |

### 6.3 答辩要点（"讲得清"）

1. **SoC 亮点不是"集成了 IP"**：讲译码与固定 2 拍应答、SRAM 三态与 CPLD 共存、**ExtRAM 双主机仲裁**、4 像素打包、**VSYNC 原子翻页握手**、confreg 的 BCD 硬件解码。
2. **为什么 800×600 而不是 640×480**：单一 50 MHz 时钟域消除 CDC，代价仅多占 5% 带宽。
3. **DVI 为什么能这么简单**：端口是并行 RGB332，TMDS 在板载发送器里；我方只做时序 + 帧缓冲 + 1 根翻页线。
4. **AI 为什么到不了 65536**：算力差 2~3 个数量级；给出节点/秒—深度—成绩三列数据。
5. **没有串口怎么调试**：靠"确定性替代可观测性"——同源编译让 PC 上的验证完全迁移到板上，配合 LED 调试位与仿真波形。
